# 역량 기준 — AI 코딩 도구가 일상이 된 뒤의 백엔드 엔지니어

> 작성 2026-11-19. 커리큘럼(M0~M8)의 **상위 기준**이다. 미션·통과 기준은 이 문서의 역량 중 하나 이상을 측정해야 한다.
> 목표 수준(CLAUDE.md) = *면접관급 시니어에게 시스템을 설명하고 실제 문제를 구체적으로 보고할 수 있다.*

**결론:** 코드를 **쓰는** 능력의 값은 내려갔고, **명세하고 · 검증하고 · 측정하고 · 진단하고 · 설명하는** 능력의 값은 올라갔다.
그리고 E3 에 따르면 이 능력은 AI 에 통째로 맡기면 **길러지지 않는다.**

## 3. 검증 — 이 기준을 믿어도 되는가

각 역량은 아래 네 가지를 **모두** 만족해야 채택한다.

| 검사 | 질문 |
|---|---|
| V1 근거 | 신뢰도 중 이상의 근거가 1개 이상 있는가 (벤더·블로그만 있으면 보류) |
| V2 측정 | PR·실행·문서로 **관찰 가능한** 판정 방법이 있는가 ("이해했다" 금지) |

| V4 목표 정합 | 목표 수준과 사용자 약점(부하 테스트·용량 산정·관측성)과 맞는가 |

**보류·제외한 것**
- *AI 에이전트 구축*(E7 1위 키워드) — 크레딧 서비스 요구사항에 필요가 없다. 억지로 넣으면 시나리오가 흐려진다. M8 이후 선택 과제 후보로만 둔다.
- *프롬프트 엔지니어링 자체* — C6 의 "프롬프트 버전별 품질 회귀" 안에서만 다룬다. 독립 역량으로 둘 근거가 없다.

## 5. AI 사용 정책 (C7) — 리뷰·판정의 기준

| 구분 | 범위 | 이유 |
|---|---|---|
| **직접** | 테스트(요구사항 정의) · 동시성 제어 · 트랜잭션 경계 · 멱등성 · 장애 진단 | 판단이 들어가고, AI 가 약하며(E6), 맡기면 학습이 안 된다(E3) |
| **허용** | DTO · 설정 · Swagger · `docker-compose` · k6/스크립트 뼈대 · 문서 서식 | 반복 코드. 단 **모든 줄을 설명할 수 있어야** 한다 |
| **언제나 허용** | 개념 질문 · 공식 문서 찾기 · 생성된 코드의 *설명* 요청 | E3 의 고득점 패턴("생성 후 이해" · "개념 질문") |

- PR 본문에 **「AI 사용 기록」**: 무엇을 맡겼나 · 무엇을 고쳤나 · 왜. 안 썼으면 "없음".
- 리뷰 때 멘토가 **임의의 줄**을 골라 설명을 요구한다. 설명 못 한 줄 = 그 줄이 속한 기준 Fail.
- 마일스톤마다 예외를 둘 수 있다(예: M0 = 전부 직접). 미션 문서가 우선한다.

### 새 과제 형식

| 과제 | 형식 | 마일스톤 |
|---|---|---|
| **AI 초안 검증** (C2) | 내 구현을 끝낸 **뒤** 같은 요구를 AI 에 맡겨 `ai-draft/m<n>` 브랜치에 둔다(머지 안 함) → **내 테스트를 초안에 돌린다** → 결함·찾은 방법을 `docs/reports/M<n>-ai-review.md` 에. 결함이 있는데 내 테스트가 통과시켰다면 = 내 테스트가 약하다 → 보강 | M2 · M3 · M5 · M6 |
| **고장 진단 드릴** (C5) | 멘토가 `drill/m<n>` 에 **설정·인프라만** 바꿔 장애를 심는다(스텁 지연·실패율, 커넥션 풀, 브로커 중단 등 — 사용자 코드 불변). 사용자는 diff 를 보지 않고 증상 한 줄만 받아 **AI 없이** 가설 → 검증. 틀린 가설도 남긴다 | M5 · M7 |
| **고정 평가셋** (C6) | 입력 20건+ · 기대 점수 범위. 프롬프트 버전 변경 시 채점 차이, 반복 시 편차. 로컬 모델로 `./gradlew test` 와 분리 | M4 |
