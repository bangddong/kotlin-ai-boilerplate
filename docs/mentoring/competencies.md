# 역량 기준 — AI 코딩 도구가 일상이 된 뒤의 백엔드 엔지니어

> 작성 2026-11-19. 커리큘럼(M0~M8)의 **상위 기준**이다. 미션·통과 기준은 이 문서의 역량 중 하나 이상을 측정해야 한다.
> 목표 수준(CLAUDE.md) = *면접관급 시니어에게 시스템을 설명하고 실제 문제를 구체적으로 보고할 수 있다.*

## 1. 근거 — 무엇이 바뀌었나

| # | 관찰 | 출처 · 신뢰도 |
|:-:|---|---|
| E1 | 개발자의 AI 사용 90%, "높은 신뢰" 3%. AI 는 처리량을 올리지만 **출시 전 의도대로 동작하는지 보장**이 약점으로 남는다. AI 는 조직의 기존 강점·약점을 증폭한다 | [DORA 2025](https://services.google.com/fh/files/misc/2025_state_of_ai_assisted_software_development.pdf) · 상 (약 5천 명 설문) |
| E2 | 가장 많은 응답(48%)이 "**쉽게 검증할 수 있을 때만**" AI 를 신뢰한다. 중요한 결정을 맡기는 비율은 6.6% | Stack Overflow 2026 설문 ([요약 기사](https://itbrief.co.uk/story/stack-overflow-survey-shows-developers-trust-ai-with-caveats)) · 중상 (원문 수치는 재확인 필요) |
| E3 | AI 를 쓴 그룹은 이해도 퀴즈가 약 17%p 낮았고, **디버깅 문항에서 격차가 가장 컸다.** 다만 "생성 후 이해" 패턴은 86%, "통째 위임"은 39% — **쓰는 방식**이 학습을 갈랐다 | [Anthropic RCT, 2026-01](https://www.anthropic.com/research/AI-assistance-coding-skills) · 상 (무작위 대조, 표본 52명) |

| E5 | AI 생성 코드의 보안 테스트 통과율 56%, **Java 는 30%** (2026). 1년 동안 거의 개선되지 않았다 | [Veracode 2026](https://sdtimes.com/agentic-security/veracode-finds-ai-generated-code-security-has-barely-improved-since-last-year/) · 중 (벤더 벤치마크) |
| E6 | LLM 이 만든 Java 동시성 코드의 버그는 **컴파일되고 기능 테스트도 통과**한다(스레드 타이밍에 의존). 기존 벤치마크는 순차 코드만 본다 | [CONCUR, arXiv 2603.03683](https://arxiv.org/abs/2603.03683) · 상 · [arXiv 2508.14727](https://arxiv.org/abs/2508.14727) · 상 · Sonar 리더보드 · 중 (벤더) |
| E7 | 백엔드 공고의 19.5%가 생성형 AI 역량을 명시하고, 그중 1위가 AI 에이전트(8.1%). 기본기(API 설계·DB·분산 시스템·관측성)는 그대로 요구된다 | [InterviewStack 공고 분석](https://interviewstack.io/blog/how-ai-is-changing-backend-developer-2026) · 중하 (블로그, 6,964건) · ManpowerGroup 2026 · 중 |
| E8 | 국내 채용: 코딩테스트 대신 **AI 를 써서 실무형 문제를 푸는** 평가가 등장했다(넥슨, 올리브영 AI-First Track). 면접은 AI 자체보다 *문제 해결 과정을 설명*하는 쪽으로 이동하고 있다 | [잡플래닛](https://www.jobplanet.co.kr/contents/news-8452) 등 · 하 (플랫폼 콘텐츠) |

**결론:** 코드를 **쓰는** 능력의 값은 내려갔고, **명세하고 · 검증하고 · 측정하고 · 진단하고 · 설명하는** 능력의 값은 올라갔다.
그리고 E3 에 따르면 이 능력은 AI 에 통째로 맡기면 **길러지지 않는다.**

| C3 | **정합성 설계** | 동시성·트랜잭션 경계·멱등성·분산 일관성. AI 가 가장 약하고 테스트로도 잘 안 잡히는 영역 | E6 |
| C4 | **측정으로 판단** | 목표치를 먼저 정하고, 같은 조건에서 수치로 비교한다. 체감은 근거가 아니다 | E1 · E4 |
| C5 | **진단** | 증상 → 가설 → 검증 순서로 원인을 좁힌다. 관측성(지표·로그·추적)을 먼저 깐다 | E3 (디버깅 격차 최대) · E7 |
| C6 | **LLM 을 시스템 부품으로** | 느리고·비싸고·한도가 있고·틀리는 외부 의존성으로 다룬다: 비용·지연·호출 한도·실패·환불·출력 검증·프롬프트 인젝션·프롬프트 버전별 품질 회귀 | E7 · 이 레포의 목적 |
| C7 | **AI 협업 방식** | 작업을 AI 에 맡길지 직접 할지 가른다. 맡길 땐 명세를 주고, 결과를 이해한 뒤 받아들인다("생성 후 이해") | E3 · E8 |

## 3. 검증 — 이 기준을 믿어도 되는가

각 역량은 아래 네 가지를 **모두** 만족해야 채택한다.

| 검사 | 질문 |
|---|---|
| V1 근거 | 신뢰도 중 이상의 근거가 1개 이상 있는가 (벤더·블로그만 있으면 보류) |
| V2 측정 | PR·실행·문서로 **관찰 가능한** 판정 방법이 있는가 ("이해했다" 금지) |
| V3 비중복 | 다른 역량과 판정 대상이 겹치지 않는가 |
| V4 목표 정합 | 목표 수준과 사용자 약점(부하 테스트·용량 산정·관측성)과 맞는가 |

| ID | V1 | V2 | V3 | V4 | 판정 |
|:-:|:-:|:-:|:-:|:-:|---|
| C1 | ✅ E1 상 | ✅ 테스트 존재·실행 | ✅ | ✅ | 채택 |
| C2 | ✅ E6 상 | ⚠️ **현재 판정 방법 없음** → 새로 만든다 | ✅ C1 은 "기준 만들기", C2 는 "결함 찾기" | ✅ | 채택 (판정 신설) |
| C3 | ✅ E6 상 | ✅ 반복 실행 테스트 | ✅ | ✅ | 채택 |

| C5 | ✅ E3 상 | ⚠️ M7 가상 장애뿐 → **실제로 고장 낸 상태의 진단**이 필요 | ✅ C4 는 "비교", C5 는 "원인" | ✅ 약점 정면 | 채택 (판정 보강) |

| C8 | ⚠️ E8 하 — 단, 목표 수준이 직접 요구 | ✅ 퀴즈·면접형 질문 0~10점 | ✅ | ✅ | 채택 |

**보류·제외한 것**
- *AI 에이전트 구축*(E7 1위 키워드) — 크레딧 서비스 요구사항에 필요가 없다. 억지로 넣으면 시나리오가 흐려진다. M8 이후 선택 과제 후보로만 둔다.
- *프롬프트 엔지니어링 자체* — C6 의 "프롬프트 버전별 품질 회귀" 안에서만 다룬다. 독립 역량으로 둘 근거가 없다.

## 5. 커리큘럼 수정 방향 (승인 후 적용)

| 공백 | 수정 | 위치 |
|---|---|---|
| C7 | **AI 사용 정책**: 직접 = 테스트·동시성·트랜잭션 경계·장애 대응 / 허용 = DTO·설정·Swagger·compose·스크립트 뼈대. PR 본문에 **「AI 사용 기록」**(무엇을 맡겼고 무엇을 고쳤나). 리뷰 때 임의의 줄을 골라 설명을 요구한다 | CLAUDE.md · 모든 미션 「제출」 |
