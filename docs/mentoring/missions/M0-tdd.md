# [M0 · STEP 01~02] TDD 로 크레딧 서비스 개발하기

> 원문: Notion 「1-1 TDD & 클린아키텍처」 — 1주차 과제 *"TDD 로 개발하기"*(포인트 → 크레딧으로 치환)

## 이번 챕터 목표

- **테스트 가능한 코드와 테스트 코드 작성에 집중하며, TDD 기반으로 요구사항 기능을 개발한다.**
- 커버리지 100% 가 아니라 **기능의 동작을 확인하는 유의미한 테스트**를 쓴다.
- 순서: ① 요구사항 검증 테스트 추가 → ② 통과하도록 구현 → ③ 리팩토링 (한 번에 큰 스코프를 잡지 않는다)

## 제공되는 것 (멘토 작성 · 🔴 수정 금지)

- Gradle 골격(Kotlin 2.1 · Java 21 · Spring Boot 4.0.x · JUnit5 · AssertJ)
- `infra/memory/` — `CreditTable`, `CreditHistoryTable` (메모리 저장소, **호출마다 무작위 지연** — 경합을 재현하기 위함)
- `CreditController` 껍데기 (엔드포인트 4개, 본문은 `TODO`)

> 원 과제와 같은 제약: *"`/database` 패키지의 구현체는 수정하지 않고, 이를 활용해 기능을 구현"*

## Default (필수)

- [ ] `CreditService` 4기능 — **잔액 조회 · 충전/사용 내역 조회 · 충전 · 사용**
- [ ] 각 기능의 **단위 테스트** (대상 객체의 의존성만 존재해야 한다 — 테스트 더블 활용)
- [ ] 테스트마다 *"이 테스트가 왜 필요한가"* 를 한 줄 주석 또는 `@DisplayName` 으로

## Step 1

- [ ] 정책 추가 — **잔고 부족 시 사용 실패 · 최대 잔고 초과 시 충전 실패** (경계값 테스트 포함)
- [ ] **같은 사용자에 대한 동시 요청이 한 번에 하나씩 처리**되도록 리팩토링
- [ ] 동시성 **통합 테스트** — 예: 잔액 0 인 사용자에게 충전 100 × 10 동시 → 최종 1,000 · 사용 혼합 시 음수 없음
- [ ] 🔑 **다른 사용자끼리는 서로 막지 않아야 한다** — 이것도 테스트로 증명 (전역 락이면 Fail)

## Step 2

- [ ] **동시성 제어 방식 분석 보고서** `docs/reports/M0-concurrency.md`
  - 고려한 방식들과 고르지 않은 이유 (예: `synchronized` · `ReentrantLock` · `ConcurrentHashMap` 기반 사용자별 락 …)
  - 🔑 **수치 하나 이상** — 예: 사용자 1명 vs 10명 동시 요청 시 소요 시간. *항해 때 남긴 숙제(수치 없음)를 여기서 처음 회수한다*
  - 이 방식이 **서버가 2대가 되면** 어떻게 깨지는가 (M3 의 예고편)

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | Default 4기능 + 단위 테스트 통과 | `./gradlew test` 실제 실행 |
| 2 | 단위 테스트가 저장소 구현에 의존하지 않는다 | 코드 리뷰 |
| 3 | 정책 경계값(정확히 최대 잔고 · 정확히 잔액만큼 사용) | 테스트 존재 + 통과 |
| 4 | 동시성 통합 테스트가 **반복 실행 10회 모두** 통과 | `./gradlew test --rerun` × 10 |
| 5 | 사용자 간 비간섭이 테스트로 증명됨 | 테스트 존재 + 통과 |
| 6 | 보고서에 비교 근거와 수치 1개 이상 | 문서 리뷰 |

> **Default 를 만족하지 못하면 Step 1·2 는 Fail** (원 과제 규칙 그대로).

2. 동시성 테스트가 *"가끔"* 통과한다면 그 테스트는 무엇을 증명하는가?
3. 이 서비스에서 LLM 호출이 크레딧 차감 사이에 끼면 락을 얼마나 오래 잡게 되는가? (M5 예고)
