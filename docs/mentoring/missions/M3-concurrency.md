## 이번 챕터 목표

- 동시성 문제(Race Condition · Lost Update · Deadlock)가 **내 시나리오의 어디에서** 나는지 정확히 짚는다.
- 해결 방식들을 **직접 구현해 보고 숫자로** 비교한 뒤 하나를 고른다.

## 동시성 후보 지점 (스스로 더 찾을 것)

- 크레딧 차감 · 충전 (같은 사용자 동시 요청)
- 무료 슬롯 30 (서로 다른 사용자 경합)
- 멱등 키 (같은 요청 동시 2회)

## 비교 대상

| # | 방식 | 비고 |
|:-:|---|---|
| 1 | 낙관적 락 (`@Version`) | 실패 시 재시도 정책까지 |
| 2 | 비관적 락 (`SELECT … FOR UPDATE`) | |
| 3 | 분산 락 (Redis · Redisson) | 락 키 단위 · **락 ↔ 트랜잭션 순서** |
| 4 | 조건부 UPDATE (`UPDATE … SET balance = balance - ? WHERE balance >= ?`) | 락 없는 원자적 갱신 — devquest `SharedRateLimiter` 참고(`reuse-from-devquest.md`) |
| 5 | (선택) Kafka 키 기반 순차 처리 | M6 예고편 — 문서 비교만으로 충분 |

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | 보고서에 방식 **3개 이상**의 측정 수치가 같은 조건으로 있다 | 문서 리뷰 + 측정 재현 |
| 2 | 채택 이유가 수치와 **충전/차감의 충돌 빈도** 특성에서 나온다 | 문서 리뷰 |
| 3 | 분산 락을 썼다면 **락 획득 → 트랜잭션 시작 → 커밋 → 락 해제** 순서가 코드로 보장된다 | 코드 리뷰 |
| 4 | 락 키가 **사용자 단위**다 (전역 락 = Fail — 원문 3-2 Summary 의 실수 사례) | 코드 리뷰 + 비간섭 테스트 |
| 5 | 통합 테스트 반복 10회 통과 | `--rerun` × 10 |
| 6 | 🆕 AI 초안 검증: 결함마다 *찾은 방법*(테스트·실측·문서)이 있고, 내 테스트를 초안에 돌린 결과가 있다. 결함이 있는데 내 테스트가 통과시켰다면 → 그 테스트를 보강했다 | 문서 + 멘토가 `ai-draft/m3` 에서 테스트 실행 |

> **기본 미달이면 심화 Fail.**
