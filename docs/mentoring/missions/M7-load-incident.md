# [M7 · STEP 19~20] 부하 테스트 · 장애 대응 — 가장 중요한 마일스톤

> 원문: Notion 「4 장애대응」
> https://app.notion.com/p/1583c401213881b0be02de540ecdd833
> 🆕 항해 때 **하지 않은** 챕터. 🔑 약점 *"부하 테스트·용량 산정·관측성 구축을 해본 적이 없다"* 를 정면으로 메운다.

## 이번 챕터 목표

- 배포 전에 **목표치(TPS · 응답 시간)**를 정하고, 부하를 걸어 확인하고, 못 미치면 원인을 찾아 고친다.
- 장애는 막을 수 없다 — **탐지 → 분류·전파 → 복구 → 회고**의 프로세스를 문서로 갖춘다.

## 이번에 처음 하는 것 — 관측성

- Actuator + Micrometer → **Prometheus + Grafana** (`docker-compose`). 부하 테스트 중 *무엇이 병목인지* 보려면 먼저 보여야 한다.
- 최소 지표: 요청 수·에러율·p50/p95/p99 · HikariCP active/pending · JVM 힙 · **LLM 호출 수·지연·대기열 길이**

## STEP 19

- [ ] **부하 테스트 계획서** `docs/reports/M7-load-test-plan.md` — 대상 · 목적 · 목표 TPS/응답 시간 · 시나리오
  - 후보: 크레딧 충전/차감 · **AI 평가 요청**(스텁 LLM 지연 2s) · **무료 슬롯 Peak**(동시 폭주)
  - 테스트 유형 선택 근거 — Load / Endurance / Stress / Peak
- [ ] **k6** 스크립트 작성·실행
- [ ] (Nice to have) Docker CPU·메모리 제한을 바꿔 가며 **적정 배포 스펙** 추정

## STEP 20

- [ ] 지표 분석 → **병목 탐색 · 개선** — 개선 전후 수치
- [ ] **(가상) 장애 대응 문서** `docs/reports/M7-incident.md` — 장애 하나를 골라(예: LLM 공급사 지연 → 커넥션 고갈) 탐지 · 등급 · 전파 · 복구 · 회고 · 재발 방지. MTTD/MTTR 을 적는다
- [ ] **최종 발표 자료** — M0~M7 을 *"실제 문제를 구체적으로 보고"* 하는 형식으로

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | 목표치가 테스트 **전에** 숫자로 정해져 있다 | 문서 커밋 순서 |
| 2 | k6 결과를 멘토가 재실행해 비슷한 수치가 나온다 | 실행 |
| 3 | 병목 주장이 Grafana 지표/스크린샷으로 뒷받침된다 | 문서 리뷰 |
| 4 | 개선 전후가 **같은 조건**에서 비교됨 | 문서 리뷰 |
| 5 | 장애 문서에 탐지 수단(어떤 지표·알림이 먼저 울리는가)이 있다 | 문서 리뷰 |
