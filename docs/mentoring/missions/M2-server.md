## 1주차 — 분석·설계 (STEP 05 · 06)

### STEP 05
- [ ] 프로젝트 **Milestone** (GitHub Projects 또는 Issue 마일스톤) — 3주 작업 계획
- [ ] 요구사항별 **분석 자료** — 시퀀스 다이어그램 / 플로우차트 (최소: AI 평가 요청 · 무료 슬롯 · 충전)
- [ ] README 에 정리 후 PR

### STEP 06
- [ ] **ERD** 설계
- [ ] **API 명세** (Endpoint · Request · Response · Error · 인증) + **Mock API** — curl / `.http` 로 호출 가능해야 한다
- [ ] 채택할 **패키지 구조 · 기술 스택** README

| # | 통과 기준 | 판정 |
|:-:|---|---|
| 1 | AI 평가 요청 시퀀스에 **LLM 실패 경로**가 있다 | 문서 리뷰 |
| 2 | Mock API 를 멘토가 `.http`/curl 로 실제 호출해 응답을 받는다 | 실행 |
| 3 | ERD 에서 락이 걸릴 컬럼(잔액)이 조회용 데이터와 분리돼 있거나, 안 나눈 이유가 있다 (원문 2-2 「테이블 설계 Tip」) | 문서 리뷰 |

## 2주차 — 비즈니스 로직 (STEP 07 · 08)

### Default
- [ ] 비즈니스 로직 + **단위 테스트** — *크레딧 차감 · AI 평가 요청 · 무료 슬롯* (단위 테스트는 대상 객체 의존성만)
- [ ] 🆕 **LLM 포트 + 스텁** — 지연(ms)·실패(예외)를 테스트에서 주입 가능. 실 공급사 어댑터는 Spring AI(도입 시점 최신 안정판)로 두되 **테스트에서 절대 호출되지 않는다**

### STEP 07
- [ ] **Swagger**(springdoc) — README 에 캡처
- [ ] 주요 비즈니스 로직 + 단위 테스트

### STEP 08
- [ ] 유즈케이스(애플리케이션 계층) + **통합 테스트**(Testcontainers)
- [ ] 🆕 프롬프트에 사용자 입력을 넣을 때 **인젝션 방어**(사용자 입력을 구분자로 감싸기 등) — 어떤 위협을 막는지 한 줄

| # | 통과 기준 | 판정 |
|:-:|---|---|
| 1 | `./gradlew test` 통과, 네트워크 차단 상태에서도 통과(실키·외부 호출 0) | 실행 |
| 2 | 잔액 부족이면 **LLM 스텁이 호출되지 않음**을 테스트가 증명 | 테스트 존재 + 통과 |
| 3 | LLM 실패 시 사용자가 받는 결과가 정의돼 있고 테스트됨 | 테스트 |

## 3주차 — 운영 품질 (STEP 09 · 10)

### Default
- [ ] 비즈니스별 **에러 코드 체계** + `@RestControllerAdvice` 글로벌 핸들러 (예외 로깅 레벨 구분)

### STEP 09
- [ ] **Filter / Interceptor** 로 관점 분리 — 최소: 요청 추적 ID(MDC) · 요청/응답 로깅
- [ ] 모든 API 가 정상 동작 (최적화 아님 — *동작하는 완성*)

### STEP 10
- [ ] 시나리오별 **동시성 통합 테스트** — 같은 사용자의 동시 AI 평가 요청에서 잔액이 음수가 되지 않는다
- [ ] **Chapter 2 회고** (블로그)

| # | 통과 기준 | 판정 |
|:-:|---|---|
| 1 | 처리 안 된 예외도 일관된 에러 봉투로 응답, 스택트레이스가 응답에 노출되지 않는다 | `.http` 실행 |
| 2 | 로그 한 줄에서 요청 추적 ID 로 한 요청의 흐름을 따라갈 수 있다 | 실행 로그 |
| 3 | 동시성 통합 테스트 **반복 10회** 통과 | `--rerun` × 10 |

> 각 주차 모두 **Default 미달이면 그 주의 STEP 은 Fail.**
