## 이번 챕터 목표

- 쿼리마다 인덱스로 부하를 줄이고, **전후를 실행 계획으로** 증명한다.
- 비즈니스 로직별 **트랜잭션 범위**를 파악하고, 느린 외부 작업(LLM)·부가 로직이 핵심 트랜잭션을 잡고 있지 않게 한다.

## STEP 15 — 기본

- [ ] 서비스의 쿼리 수집 — 자주 쓰는 쿼리 · 복잡한 쿼리 (최소: 내역 조회 · 인기 평가 유형 · 결과 조회)
- [ ] 의미 있는 양의 데이터 생성 (수십만~백만 행 — 적으면 옵티마이저가 풀스캔을 고른다)
- [ ] 인덱스 추가 **전후** `EXPLAIN (ANALYZE, BUFFERS)` · 실행 시간 비교 → `docs/reports/M5-index.md`

## STEP 16 — 심화

- [ ] **트랜잭션 범위 분석** — AI 평가 요청 흐름에서 커넥션을 잡는 구간을 그린다. OSIV 설정을 확인하고 끈다/켠다의 근거
- [ ] 🆕 **LLM 호출을 트랜잭션 밖으로** — 차감(Tx1) → LLM 호출(Tx 없음) → 결과 저장 또는 환불(Tx2). 전후 **커넥션 점유 실측**(HikariCP active 수 등)
- [ ] **사용량 이벤트**(scenario 심화 8) — `@TransactionalEventListener` 로 평가 성공에 영향 없이 외부 플랫폼(스텁) 전달
- [ ] **서비스 분리 설계 문서** — credit · ai-evaluation · usage 를 나눈다면 어디를 자르고, 분산 트랜잭션의 한계(보상 트랜잭션 · SAGA)를 어떻게 다루는가 → `docs/reports/M5-service-split.md` (M8 에서 실행한다)

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | 인덱스 전후 실행 계획·시간이 **같은 데이터**에서 비교됨 | 문서 + 재현 |
| 2 | LLM 대기 중 DB 커넥션 active = 0 임을 실측으로 보임 | 측정 로그 |
| 3 | LLM 실패 → 환불이 테스트로 증명 | 테스트 |
| 4 | 외부 플랫폼 스텁이 실패/지연해도 평가 요청은 성공 | 테스트 |
| 5 | 분리 설계 문서에 보상 트랜잭션이 **실패할 때**의 처리까지 있다 | 문서 리뷰 |

> **기본 미달이면 심화 Fail.**
