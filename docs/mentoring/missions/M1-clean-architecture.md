# [M1 · STEP 03~04] 클린 아키텍처 — 일일 무료 평가 슬롯

> 원문: Notion 「1-2 TDD & 클린아키텍처」 — 2주차 과제 *"특강 신청 서비스"*(특강 → **일일 무료 평가 슬롯**으로 치환)
> https://app.notion.com/p/1583c4012138818281e6e1f8521b398d

## 이번 챕터 목표

- **아키텍처와 테스트에 집중**하며 처음으로 DB 가 붙은 백엔드 서버를 만든다.
- 비즈니스 로직이 DB 를 모르게 한다 — Repository 를 **도메인이 정의하는 인터페이스**로 두고, JPA 는 그 구현이다(DIP).
- 레이어드 / 헥사고날 / 클린 / *Clean + Layered* 중 하나를 고르고, **고른 이유를 남긴다.** 패키지 구조만 보고도 시스템이 설명돼야 한다.

## 이번에 처음 하는 것

- PostgreSQL(`docker-compose`) + JPA 연결, 통합 테스트는 **Testcontainers**(로컬 DB 가 떠 있어야만 도는 테스트는 FIRST 의 *Independent* 위반 — 원문 2-3 Summary)
- 인프라 설정도 **직접** 한다(M0 처럼 제공되지 않는다).

## Default (필수)

- [ ] 아키텍처 준수를 위한 **패키지 설계** — README 에 구조와 선택 이유
- [ ] 슬롯 도메인 **테이블 설계** + 기본 기능: *오늘 신청 가능한 슬롯 조회 · 슬롯 신청 · 내 신청 내역 조회*
- [ ] 각 기능의 **단위 테스트** (도메인 로직은 DB 없이 테스트된다)

## Step 3

- [ ] 설계한 테이블의 **ERD** + 왜 그렇게 나눴는지 README
- [ ] 선착순 30명 이후 신청은 **실패**
- [ ] **동시에 40명**이 신청하면 **정확히 30명만 성공**하는 통합 테스트

## Step 4

- [ ] **같은 사용자**는 같은 날 슬롯을 한 번만 신청 가능
- [ ] 같은 사용자가 **동시에 5번** 신청하면 **1번만 성공**하는 통합 테스트

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | 도메인 계층이 JPA·Spring Data 를 import 하지 않는다 | 코드 리뷰 (`grep`) |
| 2 | Default 단위 테스트 통과 | `./gradlew test` 실제 실행 |
| 3 | 40 → 30 통합 테스트가 **반복 10회 모두** 통과 | `./gradlew test --rerun` × 10 |
| 4 | 5 → 1 통합 테스트가 **반복 10회 모두** 통과 | 동상 |
| 5 | 테스트가 로컬에 떠 있는 DB 에 의존하지 않는다 | `docker-compose down` 상태에서 실행 |
| 6 | ERD 와 README 가 "왜"를 설명한다 | 문서 리뷰 |

> **Default 미달이면 Step 3·4 는 Fail.**

## 면접형 질문 (리뷰 때 묻는다)

1. 30명 제한을 **애플리케이션 코드의 if 문**으로만 지키면 무엇이 깨지는가? 그걸 막은 장치는 DB 의 무엇인가?
2. "중복 신청 1회"를 **유니크 제약**으로 막았다면, 그 예외는 어느 계층에서 어떤 도메인 의미로 바뀌어야 하는가?
3. 도메인 모델과 JPA 엔티티를 **분리했는가, 합쳤는가?** 그 선택의 비용은 무엇인가? (원문 2-1 「도메인 ≠ 엔티티」)
