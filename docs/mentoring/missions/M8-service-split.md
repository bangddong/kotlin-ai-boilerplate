# [M8] 서비스 분리 — ai-api 를 별도 서비스로

> 항해 원문 없음 — **STEP 16 서비스 분리 설계(`docs/reports/M5-service-split.md`)의 실행.**
> 참고: devquest `BaseAiHttpAdapter` · `AiApiRestClientBuilder`(이중 재시도 금지 · String 기반 역직렬화) — `reuse-from-devquest.md`

## 이번 챕터 목표

- 설계 문서를 **실제로** 실행해 보고, 설계와 실제가 어디서 달랐는지 기록한다.
- 네트워크 경계가 생기면 무엇이 새로 실패하는지(타임아웃 · 부분 실패 · 중복) 몸으로 겪는다.

## Default

- [ ] AI 평가(LLM 호출) 모듈을 **별도 Spring Boot 애플리케이션**으로 분리 (Gradle 멀티 모듈 또는 별도 디렉터리)
- [ ] 두 서비스 간 통신 방식 선택(HTTP 동기 / Kafka 비동기) + 근거
- [ ] `docker-compose` 로 두 서비스 + 인프라가 함께 뜬다

## Step

- [ ] 경계 호출에 **타임아웃 · 재시도 · 서킷 브레이커** — 재시도는 **한 층에서만**(이중 재시도는 공급사 호출 수를 곱으로 늘린다)
- [ ] 분산 추적 — 요청 추적 ID 가 두 서비스 로그를 잇는다
- [ ] M7 부하 테스트를 다시 돌려 **분리 전후** 비교
- [ ] 설계 문서 대비 **달라진 점** 회고

## 통과 기준 (멘토 판정)

| # | 기준 | 판정 방법 |
|:-:|---|---|
| 1 | ai-api 를 내려도 크레딧 서비스는 살아 있고, 평가 요청은 정의된 방식으로 실패·환불된다 | 실행 (`docker stop`) |
| 2 | 재시도가 정확히 한 층에만 있다 | 코드 리뷰 |
| 3 | 한 요청을 두 서비스 로그에서 같은 ID 로 추적 | 실행 로그 |
| 4 | 분리 전후 부하 테스트 수치 | 문서 |

> **Default 미달이면 Step Fail.**

## 면접형 질문

1. 분리 후 p99 가 늘었다. 늘어난 몫은 어디서 왔는가 — 네트워크인가, 직렬화인가, 커넥션 풀인가? 어떻게 구분하는가?
2. ai-api 가 응답 직전에 죽었다. 크레딧 서비스는 *과금됐는지* 어떻게 아는가?
3. 이 규모에서 분리는 **해야 했는가?** 하지 말았어야 할 이유를 하나 들어라.
